# User Login Specification

## Purpose

User login authenticates existing users with email and password credentials, issuing a JWT token for subsequent authenticated requests.

## Requirements

### Requirement: Authenticate User via API

The system SHALL accept POST requests to `/api/auth/login` with email and password, validate credentials, and return a JWT token on success.

#### Scenario: Successful login with valid credentials

- GIVEN a user exists with email "user@example.com" and password "SecurePass123"
- WHEN POST /api/auth/login is called with `{"email": "user@example.com", "password": "SecurePass123"}`
- THEN the response status SHALL be 200 OK
- AND the response body SHALL contain `{"token": "<jwt-token>"}`
- AND the JWT token SHALL be signed with the configured secret
- AND the JWT token SHALL contain the user's ID, email, and roles in claims

#### Scenario: Login fails with incorrect password

- GIVEN a user exists with email "user@example.com" and password "SecurePass123"
- WHEN POST /api/auth/login is called with `{"email": "user@example.com", "password": "WrongPass"}`
- THEN the response status SHALL be 401 Unauthorized
- AND the response body SHALL contain `{"error": "Invalid credentials"}`
- AND no token SHALL be issued

#### Scenario: Login fails with non-existent user

- GIVEN no user exists with email "missing@example.com"
- WHEN POST /api/auth/login is called with `{"email": "missing@example.com", "password": "AnyPass123"}`
- THEN the response status SHALL be 401 Unauthorized
- AND the response body SHALL contain `{"error": "Invalid credentials"}`
- AND no token SHALL be issued

#### Scenario: Login fails with missing credentials

- GIVEN a user exists
- WHEN POST /api/auth/login is called with `{"email": "user@example.com"}`
- THEN the response status SHALL be 400 Bad Request
- AND the response body SHALL contain `{"error": "Password is required"}`

### Requirement: JWT Token Generation

The system SHALL generate JWT tokens using the existing firebase/php-jwt infrastructure, signing with HS256 and including user claims.

#### Scenario: JWT token contains required claims

- GIVEN a user with ID "abc-123", email "user@example.com", and roles ["ROLE_USER"]
- WHEN a JWT token is generated for this user
- THEN the token payload SHALL contain `sub: "abc-123"`
- AND the token payload SHALL contain `email: "user@example.com"`
- AND the token payload SHALL contain `roles: ["ROLE_USER"]`
- AND the token SHALL be signed with HS256 algorithm
- AND the token SHALL have an expiration time (e.g., 1 hour from issuance)

#### Scenario: JWT token can be validated by existing TokenValidator

- GIVEN a JWT token generated by the login flow
- WHEN the token is passed to the existing TokenValidator
- THEN the token SHALL be successfully validated
- AND the decoded payload SHALL match the original claims

### Requirement: Credential Validation

The system SHALL validate user credentials by comparing the provided password against the stored hash using Symfony's password hasher.

#### Scenario: Password verification with correct password

- GIVEN a User entity with a hashed password
- WHEN the plain password "SecurePass123" is verified against the hash
- THEN verification SHALL succeed

#### Scenario: Password verification with incorrect password

- GIVEN a User entity with a hashed password for "SecurePass123"
- WHEN the plain password "WrongPass" is verified against the hash
- THEN verification SHALL fail
